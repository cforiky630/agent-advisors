# 软件设计与架构工程顾问 (Software Design Advisor)

> 本文档为 `SKILL.md` 的中文对照参考文档。Agent 在机器执行时优先读取 `SKILL.md`（纯英文工业规范），人类开发者可查阅本文档理解其全套设计。

本顾问作为技术专家，整合了软件工程领域的 **14 部传世经典著作**，旨在为架构决策、模块抽象、代码构造、遗留系统改造、重构与代码评审提供系统化的权威指导。

**核心指导原则：构建纪律、降低缺陷率、深模块封装、人类可读性，坚决反对炫技与教条主义。**

| 工程领域 (Engineering Domain) | 核心指导经典 (Foundational Classic) | 核心关注点 (Primary Focus) |
| :--- | :--- | :--- |
| **日常代码构建 / 命名 / 防御性** | **《代码大全》(Code Complete)** & **《程序员修炼之道》** | 见名知意、扁平控制流（Guard Clauses）、消灭魔数、DRY 原则、正交性设计 |
| **模块封装 / 接口设计 / 复杂度控制** | **《软件设计哲学》(Philosophy of Software Design)** | **深模块（Deep Modules）**：窄接口隐藏海量复杂实现；消灭透传浅方法与浅类 |
| **代码坏味道消除 / 标准重构手法** | **《重构》(Refactoring)** & **《重构与模式》** | 坏味道驱动（Code Smells）、小步快跑、保护既有行为、70+ 种标准 OOP 重构与模式 |
| **遗留系统改造 / 无测试代码治理** | **《修改代码的艺术》(Working with Legacy Code)** | 寻找接缝（Seams）、破除依赖环、在改动前建立特征测试（Characterization Tests） |
| **核心业务建模 / 复杂领域驱动设计** | **《DDD 原典》** / **《实现 DDD》** / **《DDD 精粹》** | 统一语言、限界上下文（Bounded Context）、聚合根边界、实体/值对象、防腐层（ACL） |

## 2. 经典流派哲学冲突仲裁原则

当不同经典著作的建议发生冲突时，严格按照以下仲裁规则执行：

1. **函数与类的拆分粒度（深模块 vs 微型函数）**：
   - **仲裁结果：优先遵从《软件设计哲学》的“深模块”原则。**
   - 严禁为了教条迎合《Clean Code》“函数不能超过 4 行”而将逻辑切得支离破碎。每个函数和类必须提供**实质性的抽象价值**。
   - 严禁只有 1 行调用的透传方法（Pass-through methods）和无实际封装价值的浅类。保持接口极简，内部实现具备深度。
2. **重构 vs 功能变动（Two Hats 原则）**：
   - **仲裁结果：时间与批次上的绝对分离。**
   - 绝不在同一个 PR 或修改批次中同时进行“结构重构”和“业务新增/Bug修复”。重构必须在自动化测试保护下确保外部行为严格不变。
3. **遗留代码改造策略**：
   - **仲裁结果：遵循 Michael Feathers。** 没有自动化回归测试保护前，绝不盲目重构老代码。先通过“接缝”技术植入特征测试，锁定当前行为后再实施重构。
4. **错误处理策略**：
   - **首选策略（设计哲学）**：通过重新定义接口语义，把异常情况“定义出界”（Define errors out of existence），让正常流程自然消化边界。
   - **备选策略（代码大全）**：内部逻辑假设使用断言（Assertions）及早暴露；外部信任边界使用显式领域错误，绝不静默吞掉异常（严禁 `except: pass`）。
5. **架构适度性与 DDD 落地（YAGNI vs 完整 DDD）**：
   - 杜绝过早引入复杂架构。对于简单 CRUD，采用务实分层；仅当存在高频冲突或复杂业务不变量（Invariants）时，才引入聚合根与领域事件。

## 3. 核心流派 Nano 级硬规约

### A. 构造与实效守则 (Code Complete & Pragmatic Programmer)
- **显式意图**：变量与函数命名必须揭示业务含义，杜绝 `temp`, `data`, `flag` 及无解释魔数。
- **杜绝模式开关**：禁止通过传入布尔参数（Boolean Flags）在函数内部走不同分支，必须拆分为独立的具名函数。
- **守卫边界**：优先使用 Guard Clauses 提前返回，嵌套深度控制在 3 层以内。
- **边界防御**：在网络、文件、外部用户输入交界处强制严格校验；严禁在非法或已损坏状态下继续运行。

### B. 模块与封装守则 (Philosophy of Software Design)
- **深模块优先**：模块的品质取决于“收益与成本比”。优秀设计的特征是“最简单的接口呈现，封装最具深度的逻辑”。
- **信息隐藏（Information Hiding）**：模块内部的数据结构、存储细节及私有辅助方法严禁外泄。
- **适度通用接口**：模块接口应适度保持通用性，以隐藏上层业务特殊的编排细节。

### C. 演进与遗产治理 (Refactoring & Legacy Code)
- **坏味道驱动**：只针对明确的 Code Smells（发散式变化、散弹式修改、基本类型偏执等）发起重构，不凭空改造。
- **接缝技术（Seam）**：对于强耦合的遗留代码，在不改变原有源码的前提下寻找接缝，建立拦截与测试切入点。

### D. 架构、领域与韧性 (Clean Arch, DDD, PoEAA & DDIA)
- **依赖单向流入**：依赖规则必须指向高层策略。内部业务领域实体绝对不依赖外层 UI、数据库、网络驱动或第三方 SDK。
- **充血模型**：业务规则与数据校验收拢在实体（Entity）与值对象（Value Object）内部。
- **防御级联失效**：分布式外部调用必须设置严格超时、断路器（Circuit Breaker）和降级兜底方案。

## 5. 交付前工程自检清单

在输出最终设计、重构方案或生成代码前，逐项自检：
1. **[ ] 人类心智负担**：控制流是否扁平直观？命名是否无需解释？
2. **[ ] 模块深度**：接口是否足够精简？内部实现是否充分隐藏，杜绝透传浅方法？
3. **[ ] 遗留代码安全**：若修改老代码，是否有测试或接缝保护现有逻辑？
4. **[ ] 信任边界**：所有外部输入是否都有校验防御？异常是否有完整上下文且无静默掩盖？
5. **[ ] 架构正交性**：核心逻辑是否与框架解耦？依赖方向是否单向内流？
6. **[ ] 分布式韧性**：若涉及外部 I/O 与分布式调用，是否有超时与熔断降级考量？
